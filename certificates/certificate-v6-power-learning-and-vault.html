Top 2 Improvements

  1. Pause the RAF loop when the dial is not moving In ExpeditionLock.jsx, the dial spin RAF loop runs unconditionally while the modal is open. During "rest" beats (typically 50–60% of pattern time), JAM state (miss recovery, ~450ms), and crack celebration → onClose transition, the dial could be driven by CSS transition or the RAF loop cancelled and re-requested. Simplest fix: track a movingRef boolean; cancel the RAF when speed becomes 0 or during jam; re-request when movement resumes. This eliminates continuous CPU wake (~60fps) during the majority of a vault session.
    ⚡ Energy impact: eliminates ~40–60% of the RAF CPU cost during vault interaction. Small in absolute terms (modal is short-lived) but it's the right pattern and avoids accumulation if multiple modals opened in a session.
    Evidence: ExpeditionLock.jsx lines 22–30 (constants), RAF usage in dial rotation section
  2. Pin Carbon React to a minor version in package.json Currently "@carbon/react": "^1.33.0" — the ^ prefix allows automatic minor updates. Carbon is a large design system (~400KB+ gzipped). An unexpected minor version bump can add tree-shaken-but-still-present components. Pin to an exact version ("@carbon/react": "1.33.0") and update deliberately. This is already correctly done for react and react-dom in the Power learning app, but not for Carbon itself.
    ⚡ Energy impact: avoids silent bundle size growth from auto-updated dependencies on every fresh npm ci build (which runs in every Docker build and every Code Engine deployment).
    Evidence: package.json line 7 — "@carbon/react": "^1.33.0"
Highlight — structurally excellent energy decisions: This application makes three energy-correct architectural choices by default: (1) static site with no per-request server compute, (2) scale-to-zero hosting so idle = zero consumption, (3) all game state client-side so no database round-trips during gameplay. These are not accidents — they are the right tool for a lightweight learning app. The C→B improvement path is about polishing the animation loop, not structural change.

Two-Axis Context

Language Multiplier

~21.5×
JavaScript (Next.js + Node.js/Express). Same Tier 4 structural ceiling as Project 1. Correct language choice for a pre-sales demo: rapid development, Carbon Design System, WebSocket support for real-time progress. The demo purpose justifies the language overhead — these are short-lived demo sessions, not sustained production workloads.

Algorithmic Efficiency

C
Good patterns: idempotent Vault PKI setup, event-driven WebSocket progress (no polling), explicit error handling for already-mounted secrets engines. Main concern: the server emits WebSocket events on every line of SSH script output — including verbose colour-code lines from the shell scripts. No rate limiting on socket emissions.

Component Ratings — Evidence

Component Rating Finding Evidence
Vault PKI setup — idempotency A The setup-pki route correctly handles the "already mounted" case (HTTP 400 from Vault = no-op, not an error). Checks for existing CA before generating a new root. Safe to re-run on every demo provision without double-work. This is an explicit energy-efficiency design: don't redo what is already done. vault.js lines 21–26, 33–37
WebSocket real-time progress (vs polling) A Certificate replacement progress is pushed over WebSocket (socket.io) as events fire. No client polling loop. The UI receives a progress line only when something happens on the AIX side, not on a tick. Correct event-driven pattern. vault.js lines 96–121; server/index.js lines 30–43
SSH script execution — streaming output B The runScriptOnAIX helper streams SSH output line-by-line via onOutput callback rather than buffering the entire remote execution output in memory. For a script that creates 150 certificates this avoids holding a potentially large string buffer. setup.js lines 27–37; vault.js lines 105–121
Socket.io emission filtering — replace route C The vault replace route only emits a WebSocket event for lines containing "Replaced:" — correctly filtering signal from noise. However the setup route (generate-certificates) emits every output line: req.io.emit('setup:status', { step: line, progress: 50 }). The shell scripts use colour escape codes and verbose section headers — these all generate socket events to every connected client. setup.js line 35 (unfiltered); vault.js line 118 (filtered — good)
Server startup logging C WebSocket connect/disconnect logs every client event unconditionally: console.log(`[ws] client connected: ${socket.id}`). During a demo, Next.js HMR and the UI both open WebSocket connections — these fire repeatedly on page reloads. Each console.log forces a synchronous write to stdout (in Node.js default mode). Not a major concern for a demo app, but trivially removable. server/index.js lines 34–36
Dependency pinning — Next.js 13 + TypeScript B Most dependencies are pinned to exact versions (next: 13.4.9, react: 18.2.0, typescript: 5.9.3). This prevents silent bundle growth on reinstall. socket.io, express, axios use semver ranges (^) — minor concern for a demo. package.json lines 13–29
Deploy script — deploy-demo.sh C No unconditional dnf update (unlike the Carbon GenAI demo — this is better). Node.js install is conditional: only runs if not found or version < 18. However, the script checks prerequisites on every run including SSH key generation and a live AIX connection test — some steps that could be cached or skipped if the environment is already configured. deploy-demo.sh lines 51–75 (conditional Node install — good); lines 95–117 (SSH check always runs)
OpenSSL certificate generation — 150 certs on AIX D The demo creates 150 realistic "old" certificates (RSA 1024, SHA-1, backdated) via generate-old-certificates.sh on AIX for every demo setup. These are intentionally weak/expired certificates for the "before" state of the PowerSC scan. Running 150 sequential OpenSSL operations is CPU-bound and takes significant time. This is inherent to the demo narrative — the waste is the point. However, if the demo is re-run frequently, pre-generating the certificates once and resetting from a snapshot would be more efficient. deploy-demo.sh lines 284–310 (README excerpt listing 150 certs); generate-old-certificates.sh purpose
Vault certificate issuance — idempotent batch B The replace step calls /v1/pki/issue/sap-oracle via Vault API — short-lived 24h certificates issued on demand, not pre-stored. Vault handles the crypto efficiently. The route is HTTP POST (not polling) and uses the existing PKI role configured in setup. Clean architecture for a PKI demo. vault.js lines 84–131 (replace-certificates route)

Top 3 Improvements

  1. Filter socket emissions in generate-certificates route (match the vault route pattern) In setup.js line 35, every SSH output line is emitted as a WebSocket event. The vault route correctly filters to only emit meaningful lines (line.includes('Replaced:')). Apply the same filter to the setup route — emit only lines containing percentage/count progress markers, or consolidate to a single "N certificates created" event at the end. Change: if (line.includes('Creating') || line.includes('✓') || line.includes('Complete')) { req.io.emit(...) }
    ⚡ Eliminates ~200+ unnecessary WebSocket events per demo setup run. More importantly, avoids rendering 200 line updates in the UI unnecessarily.
    Evidence: setup.js line 35
  2. Gate WebSocket connection logging behind DEBUG env var Move the console.log on connect/disconnect in server/index.js lines 35–36 behind if (process.env.DEBUG). In demo use, the Next.js frontend may reconnect multiple times (HMR, page reload) generating log noise. This is the same pattern recommended for the Carbon GenAI proxy in v2: make debug logging opt-in, not default.
    ⚡ Minor but consistent with the principle: don't do I/O you don't need to do.
    Evidence: server/index.js lines 34–36
  3. Pre-bake the "old certificate" state as a TechZone snapshot The 150 RSA-1024/SHA-1 certificates need to exist on the AIX client before the PowerSC "before" scan. Currently generated fresh each time via generate-old-certificates.sh. If the TechZone environment supports custom images or snapshots, pre-generate these once and save as the baseline image. The demo resets to the snapshot before each showing rather than regenerating. This is an infrastructure-layer efficiency gain — the AIX CPU running 150 sequential OpenSSL key-gen operations is saved on every subsequent demo run.
    ⚡ Eliminates repeated AIX CPU work. More reliable demo (no risk of OpenSSL failures during a customer call). Faster demo startup.
    Evidence: deploy-demo.sh README section lines 284–310; generate-old-certificates.sh (creates 150 certs per run)
Note on demo-specific context: This is a pre-sales demo, not a production system. It runs for hours, not years. The "D-rated" certificate generation is intentional — creating weak certificates is the whole point of the demo narrative. The Jevons' Paradox risk here is effectively zero: a demo runs a bounded number of times. The energy framing is still useful for two reasons: (1) it models good habits for when demo code becomes production code; (2) the TechZone environment it runs on is shared infrastructure — good citizenship matters.
