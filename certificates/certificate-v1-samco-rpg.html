Three-Stage Modernisation Journey

F Stage 1: Legacy RLA

ART200 — Fixed-format RPG, RLA Record-Level Access
100 records: 300 DB ops (READ + 2× CHAIN/row)
Batch 10,000 rows: 10,000 individual UPDATEs
Relative energy: Baseline — 100%
ART200.PGM.SQLRPGLE (RLA path)

C Stage 2: SQL Cursor

ART301 / ORD200 — Free-format SQLRPGLE, SQL cursor + JOIN
100 records: 3 DB ops (OPEN + FETCH loop + CLOSE)
Batch 10,000 rows: 1 UPDATE statement
Relative energy: ~1–3% of baseline
ART301.SQLRPGLE, ORD200.PGM.SQLRPGLE

A Stage 3: REST API

ART400 — Free-format, no-main, IWS-ready, single-query procedures
100 records: 1 DB op (SELECT A JOIN F JOIN V)

Relative energy: ~0.3–1% of baseline

Methodology

Primary metric: Database I/O operations per business transaction — a valid energy proxy on IBM i/Power where each RLA operation involves SLIC-level dispatch, buffer pool interaction, and record lock/unlock cycles.

Limitation: This is a per-transaction rating. Net energy impact depends on whether total transaction volume remains stable (Jevons' Paradox risk: low short-term for an operational system not at capacity ceiling; monitor over 1–2 years as efficiency may enable new features that add load).

Key insight: RPG is inherently near C/Rust in language-level energy efficiency. All gains shown here are algorithmic — eliminating N+1 I/O patterns. The codebase moved from F to A without changing language or platform.
