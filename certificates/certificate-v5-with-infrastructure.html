Important caveat: the code optimisation applies to the workload-variable portion of CPU energy — not the server's idle power floor. A Power system uses roughly constant energy for OS, memory, I/O bus, and idle processes regardless of query count. So the multiplication effect is real but applies to the variable load component. On a heavily loaded server, this is significant; on a lightly loaded one, the absolute saving is smaller even if the proportional I/O saving is the same.

The practical implication: Responsibob savings convert most directly to energy when the server is near capacity, because that is when fewer I/O operations translates to genuinely avoided compute cycles rather than just wider idle headroom.

Utilisation — The Binding Factor

✓ High utilisation multiplies both savings

The E1150's 76% headroom only delivers its energy efficiency if filled with useful, consolidated workloads. An underutilised server has already paid the idle power cost — adding more work to it has near-zero marginal energy cost.

Derek's framework (Turbonomic ARM) measures and optimises this. Responsibob creates the headroom. Together they ensure it is used sustainably.

Code efficiency creates consolidation opportunity

SAMCO ART400 running 300× fewer I/O ops means the same IBM i LPAR can serve more users, more applications, or more throughput before needing additional hardware.

This is the link between Layers 3 and 2: code efficiency reduces the performance demand that determines how many servers you need. Fewer servers = less embodied carbon, less cooling, less rack space.

Positioning — v5

Infrastructure saves 39% — a real, one-time capital event validated by IBM's own estimator and consistent with Defra's 40% "design clever" band. Code efficiency (Responsibob) saves up to 20% of workload-variable energy continuously, at no capital cost, and enables the consolidation that makes the infrastructure saving sustainable at scale.

For IBM i organisations specifically: staying on IBM Power and refreshing hardware generations (E950→E1150) while modernising code (RLA→SQL) is the most energy-efficient path. The platform's per-watt advantage, the RPG language's Tier 1 energy profile, and the availability of real measurement tools (IBM Energy Estimator, QSYS2 performance data) make this a quantifiable, certifiable journey — not just an aspiration.

The unifying message: hardware efficiency and code efficiency are not in competition. The most efficient outcome requires both — modern hardware at high utilisation running code that has been optimised to do as little unnecessary work as possible. Responsibob is the tool for the code layer. The Energy Estimator is the tool for the hardware layer. Together they cover the two most actionable levers in the Defra curve.
